# 비용 관리

LLM 비용은 예상보다 빠르게 쌓일 수 있습니다. 아래 순서대로("공짜 개선" 먼저, 트레이드오프가 있는 것 나중에) 검토하는 것을 권장합니다.

## 1. 프롬프트 캐싱 (가장 먼저 검토)

- 반복되는 시스템 프롬프트, 도구 정의, 긴 문서를 캐싱하면 같은 내용을 다시 보낼 때 비용이 크게 줄어듭니다.
- 캐시가 잘 동작하는지는 응답의 `usage.cache_read_input_tokens` 값으로 확인합니다. 반복 요청인데 이 값이 계속 0이면 어딘가에서 매번 프롬프트 앞부분이 바뀌고 있다는 뜻입니다 (예: 타임스탬프, 정렬되지 않은 JSON, 매번 달라지는 도구 목록).
- 자세한 배치 원칙은 [프롬프트 작성 가이드](02-프롬프트-작성-가이드.md)의 "캐싱을 고려한 프롬프트 구조" 참고.

## 2. Effort 레벨 조절

- `output_config.effort`: `low` / `medium` / `high`(기본) / `xhigh` / `max`
- 코딩·장기 에이전트 작업은 effort를 높이면 품질이 크게 좋아지는 경향이 있고, 단순 분류/채팅/대량 처리는 `low`나 `medium`으로도 충분한 경우가 많습니다.
- 무작정 `max`로 올리기보다, 실제 요청 샘플로 측정한 뒤 필요한 라우트에만 높은 effort를 적용하세요.

## 3. 배치 처리 (Message Batches)

- 실시간 응답이 필요 없는 대량 작업(예: 야간 일괄 처리)은 Batches API를 쓰면 **50% 할인**된 비용으로 처리할 수 있습니다.
- 결과는 순서 보장이 안 되므로 `custom_id`로 매칭해야 합니다.

## 4. 모델 선택은 마지막 카드

- 비용을 줄이겠다고 임의로 하위 모델(Sonnet, Haiku)로 다운그레이드하지 않습니다. 이는 품질에 직접 영향을 주므로 팀 논의를 거쳐 명시적으로 결정합니다.
- 오히려 최신 상위 모델을 낮은 effort로 쓰는 것이 구세대 모델을 높은 effort로 쓰는 것보다 품질/비용 면에서 나은 경우가 많습니다.

## 체크리스트

- [ ] 시스템 프롬프트/도구 정의가 안정적이고 캐시 가능한 구조인가?
- [ ] `cache_read_input_tokens`가 정상적으로 찍히는가?
- [ ] 라우트별로 필요한 effort 수준을 측정해봤는가?
- [ ] 실시간이 필요 없는 작업을 배치로 옮길 수 있는가?
- [ ] 모델을 바꾸기 전에 캐싱/effort/배치를 먼저 검토했는가?
