# 프로젝트 안내 (작업하는 에이전트가 반드시 읽을 것)

## 사용자 정보
- 초등학교 교사이며 코딩 비전공자, 바이브 코딩을 시작한 지 약 1주일.
- 터미널/코드에는 익숙하지 않지만 "배포"처럼 바이브 코딩에서 자주 쓰는 기본 용어는 이미 알고 있다. 이런 용어까지 매번 풀어 설명할 필요는 없고, 정말 생소한 용어가 나올 때만 짧게 덧붙여 설명한다.
- 개발 도구(스킬, MCP, 라이브러리 등) 선택은 에이전트가 후보를 추천하고, 사용자가 고른 것으로 진행한다. 임의로 정해서 진행하지 않는다.

## 만드는 것의 목적
- 교실/수업에서 바로 쓰는 교육용 프로그램(학생용, 수업 보조용 등).
- 사용자 본인과 학생, 동료 교사가 설치 없이 바로 실행할 수 있어야 한다.
- 인터넷이 안 되는 교실에서도 돌아가면 더 좋다(가능하면 오프라인 동작 고려).

## 결과물 형식 우선순위
1. **단일 HTML 파일** — 더블클릭하면 브라우저에서 바로 열리는 형태를 최우선으로 한다. 서버 실행, 설치, 명령어 입력이 필요 없어야 한다.
2. 꼭 필요할 때만 Artifact로 배포해 링크 하나로 공유한다.
3. 실행파일(.exe 등)이나 별도 설치가 필요한 형태는 정말 불가피할 때만 마지막 선택으로 고려하고, 그 전에 사용자에게 이유를 먼저 설명한다.

## 코딩 원칙
- 화려한 기능보다 "확실히 작동하는 것"을 우선한다.
- 외부 라이브러리는 꼭 필요한 경우에만, 설치 없이 쓸 수 있는 것 위주로 쓴다.
- 코드를 고칠 때마다 실제로 브라우저에서 열어 눈으로 확인한 뒤에만 "완료"라고 보고한다.
- (2026-08-31 변경) 학생 이름·검사 결과는 **선생님이 로그인하면 자기 반 결과를 불러올 수 있도록 서버에 저장하는 것으로 원칙을 바꿈** (원래는 "절대 서버 저장 금지"였으나, 학생 관리 기능을 위해 사용자가 직접 이 변경을 확정함 — [11번 진행상황](11-진행상황.md) 참고). 다만 이건 학생 개인정보를 다루는 민감한 변경이므로, 실제로 구현할 때는 로그인 보안(비밀번호 등 안전한 인증), 선생님 본인 반 데이터만 보이게 하는 접근 제어, 저장되는 항목을 이름+점수 등 꼭 필요한 최소한으로 제한하는 것을 반드시 함께 설계한다. 얼굴 사진처럼 원래도 불필요했던 정보는 여전히 다루지 않는다.
- 학생 개인정보는 위 서버 저장 기능 외의 용도로는(예: 음성 인식 요청 등) 서버로 전송하지 않는다.
- API 키 같은 비밀 정보는 코드에 직접 적지 않는다.

## 에이전트의 설명 태도
- 사용자의 요청을 명확히 이해하지 못했다면 짐작으로 진행하지 말고, 먼저 되물어서 이해를 확인한 뒤에 작업을 시작한다.
- 새 작업을 시작하기 전, 무엇을 왜 만드는지 한두 문장으로 먼저 말한다.
- 정말 생소한 용어만 짧게 뜻을 덧붙인다. 기본적인 용어(배포, 코드, 파일 등)는 다시 설명하지 않는다.
- 완성 형태, 유료 서비스 사용 여부, 개발 도구 선택처럼 방향을 크게 바꾸는 결정은 진행 전에 반드시 먼저 확인한다.
- 실행 방법이 더블클릭이 아니라 별도 절차가 필요할 때만 결과물 마지막에 안내한다.
- 오류가 나면 어려운 로그를 그대로 보여주지 말고 "무엇이 문제였고 어떻게 고쳤는지"를 짧게 요약한다.

## 큰 변경 전에는 반드시 먼저 물어본다
- git push, 원격 저장소 관련 작업.
- 버그 수정 수준을 넘어서는 코드 전면 재작성/구조 변경.
- 위에서 다룬 완성 형태·개발 도구·유료 서비스 같은 방향 결정.
- 반대로 **간단한 버그 수정**이나 사소한 수정은 바로 진행하고 결과만 보고한다.

## 백업 습관
- git push처럼 정식으로 저장소에 올리지 않더라도, 코드를 전면 수정하거나 구조를 바꾸기 전에는 지금 파일을 복사해 `-backup` 등을 붙인 이름으로 남겨둔다.
- 백업해두었다는 사실과 파일 위치를 사용자에게 짧게 알려준다.

## git push 전 습관 (2026-09-02 확정)
- git push하기 전에는 백업 습관과는 별개로, 매번 아래 두 가지를 거치는 것을 습관화한다.
  1. **작업 내역 정리**: 이번에 push할 변경사항이 무엇인지 정리한다. 특히 여러 세션에 걸쳐 이어서 작업할 때는 [11번 진행상황](11-진행상황.md) 문서가 지금까지 한 일을 빠짐없이 반영하고 있는지 확인하고, 빠진 내용이 있으면 채워 넣는다.
  2. **코드 리뷰 및 정리**: push하기 전에 실제로 바뀐 코드를 다시 훑어보면서, 디버그용으로 남겨둔 임시 코드·죽은 코드·중복된 로직이 없는지 점검하고 정리한다. 필요하면 `/code-review` 스킬을 사용한다.
- 이 절차를 마친 뒤에만 git push를 진행하되, push 자체는 위 "큰 변경 전에는 반드시 먼저 물어본다" 규칙에 따라 사용자에게 먼저 알리고 진행하는 것은 그대로 유지한다.

## 모델/도구 선택 기본값
- Claude 모델은 별다른 요청이 없으면 최신 상위 모델을 사용한다(비용을 이유로 임의로 낮추지 않는다).
- 어떤 스킬/도구/라이브러리를 쓸지는 에이전트가 후보와 이유를 추천하고, 사용자가 선택하면 그것으로 진행한다.

- [ ] git push 전이라면, 작업 내역 정리(11번 문서 갱신) + 코드 리뷰/정리를 먼저 했다.
