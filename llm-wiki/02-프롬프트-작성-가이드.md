# 프롬프트 작성 가이드

## 기본 원칙

1. **목표를 명확히 밝힌다.** "무엇을 하려는지"와 "왜 필요한지"를 함께 적으면 모델이 더 정확한 결과를 냅니다.
2. **맥락을 충분히 제공한다.** 이미 알고 있는 제약 조건, 시도해본 것, 원하지 않는 결과를 함께 알려주세요.
3. **출력 형식을 지정한다.** JSON, 표, 목록 등 원하는 형식이 있으면 명시적으로 요구하세요. 구조가 엄격해야 한다면 API의 structured output(`output_config.format`) 기능을 사용하는 것이 프롬프트로만 형식을 강제하는 것보다 안정적입니다.
4. **예시를 든다(few-shot).** 애매한 작업일수록 입력-출력 예시 1~2개가 설명보다 효과적입니다.
5. **역할을 부여할 때는 과하게 하지 않는다.** 최신 모델(Opus 5, Sonnet 5 등)은 장황한 페르소나 설정 없이도 지시를 잘 따릅니다. 불필요하게 긴 시스템 프롬프트는 캐싱 효율을 해칠 수 있으니 핵심만 남깁니다.

## 시스템 프롬프트 vs 사용자 메시지

- **시스템 프롬프트**: 대화 전체에 적용되는 고정 규칙, 역할, 출력 형식 지침. 자주 바뀌지 않는 내용을 넣어야 캐싱 효율이 좋습니다.
- **사용자 메시지**: 매 요청마다 달라지는 실제 질문/데이터.
- 대화 도중 규칙을 바꿔야 할 때(Opus 5/Opus 4.8 계열, no beta): 최상위 `system`을 수정하지 말고 `messages` 배열에 `{"role": "system", ...}` 메시지를 추가하면 캐시된 이전 대화가 무효화되지 않습니다.

## 캐싱을 고려한 프롬프트 구조

요청은 `tools` → `system` → `messages` 순서로 렌더링되고, 앞부분이 한 글자라도 바뀌면 그 뒤 전체 캐시가 무효화됩니다. 따라서:

- 안정적인 내용(고정 시스템 프롬프트, 도구 목록)은 앞쪽에 배치
- 매번 달라지는 내용(타임스탬프, 요청 ID, 실제 질문)은 뒤쪽에 배치

## 흔한 실수

- 프롬프트에 `datetime.now()` 같은 매번 바뀌는 값을 시스템 프롬프트 앞부분에 넣으면 캐시가 매번 깨집니다.
- 도구 목록 순서가 매 요청마다 바뀌면 캐시 히트율이 떨어집니다. 정렬을 고정하세요.
- 하지 말아야 할 것을 나열하는 부정문보다, 원하는 동작을 직접 지시하는 긍정문이 더 잘 작동하는 경우가 많습니다.
