## 확정된 결정

- **음성인식/발음판정**: Azure AI Speech의 발음 평가(Pronunciation Assessment) 사용 ([10번](10-음성인식-기술-선택.md) 참고). Web Speech API는 사용하지 않음(발음 오류를 놓치기 쉬움).
- **배포**: 발표 당일 외부에서 접속 가능해야 하므로 **Vercel에 배포**한다.
- **버전 관리**: 사용자가 컴퓨터 두 대로 작업하므로 **GitHub 저장소를 만들어 두 컴퓨터를 동기화**하고, Vercel을 이 저장소에 연결해 push할 때마다 자동 배포되게 한다 (CLI 직접 업로드 대신 이 방식으로 결정함, 2026-08-31). git push는 계속 [00번 가이드](00-프로젝트-에이전트-가이드.md)의 "큰 변경 전 확인" 규칙을 따른다 — 저장소 최초 생성/연결은 승인받았지만, 이후 개별 push도 매번 먼저 알린다.
- **API 키 보관**: Azure 키는 Vercel 서버리스 함수(`/api/get-token` 같은 엔드포인트)에서만 사용하고, 이 함수가 10분짜리 임시 토큰을 발급해 브라우저에 내려준다. 진짜 키는 Vercel 환경 변수에만 저장하고 코드에는 넣지 않는다.
- **개인정보**: 학생 이름·학번 등 식별정보는 음성 요청과 함께 절대 전송하지 않는다. 세션은 임시 라벨로만 구분한다.

## 알려진 문제

- **`npx vercel dev`가 이 컴퓨터에서 안 됨.** 컴퓨터 이름 자체가 "3F교사연구실1"로 한글이라 Vercel CLI 내부에서 로그인/텔레메트리 요청을 만들 때 오류(`Cannot convert argument to a ByteString...`)가 남 (환경 버그, 컴퓨터 이름을 영문으로 바꾸고 재부팅해야 근본 해결됨 — 지금은 급하지 않아 보류).
  - **다만 이것이 최종 배포를 막지는 않는다.** 실제 배포는 GitHub 연결 + Vercel 대시보드 빌드로 이뤄지며 로컬 CLI 로그인이 필요 없다.
  - 로컬 개발 중 테스트용으로 `dev-server.mjs`(vercel 없이 순수 Node로 `index.html`과 `api/get-token.js`를 서빙)를 대신 사용 중. 실행: `node dev-server.mjs` → http://localhost:3000
- **(1차 시도, 원인 파악됨) 짧은 음절이 다른 소리로 인식되던 문제.** 처음엔 "아"만 말해도 이상해서 짧은 음절의 한계인 줄 알았는데, 사용자가 "고양이 나비"라고 말했는데도 "아 아, 100점"이 뜨는 걸 발견함 — 이건 단순 한계가 아니라, 브라우저 SDK의 `enableMiscue` 옵션이 실제로 작동하지 않는 **알려진 SDK 버그**였음 ([MS Q&A](https://learn.microsoft.com/en-us/answers/questions/1182046/enablemiscue-parameter-not-working-when-using-java) — enableMiscue를 true로 줘도 결과가 안 바뀐다는 동일 증상 보고, 마이크로소프트 담당자도 SDK 버그 가능성 인정). 이 버그가 있는 WebSocket 기반 SDK 경로(`SpeechRecognizer.recognizeOnceAsync`)를 버리고, **REST API로 직접 녹음 파일을 보내 채점하는 방식**으로 교체함 (아래 "완료된 작업" 참고). 아직 실사용 테스트로 재확인 전이라 완전히 해결됐는지는 다음 세션에서 검증 필요.

## 완료된 작업

1. 프로젝트 구조: `index.html`(화면 전체) + `api/get-token.js`(Azure 임시 토큰 발급 서버리스 함수) + `.gitignore`(`.env.local` 등 비밀 파일 제외) + `dev-server.mjs`(로컬 테스트용).
2. 1~6단계 샘플 문항(각 3개)과 화면 흐름(단계 선택 → 듣기 → 말하기 → 결과) 구현 완료.
   - 듣기: Azure 고품질 한국어 음성(`ko-KR-SunHiNeural`)으로 모범 발음 재생 (처음엔 브라우저 내장 TTS를 썼다가 발음 품질이 안 좋아서 교체함).
   - 말하기: 처음엔 Azure Speech SDK(`SpeechRecognizer`, 웹소켓)로 구현했으나, `enableMiscue` SDK 버그 + "다시 누르면 취소만 되고 채점이 안 됨" 문제 때문에 마이크를 직접 녹음(버튼 다시 누르면 녹음 종료) → 녹음 파일을 Azure REST 발음 평가 API로 전송해 채점하는 방식으로 교체함.
     - 1차 시도(MediaRecorder로 webm 녹음): REST 응답 구조를 잘못 읽어서(`NBest[0].PronunciationAssessment.AccuracyScore`가 아니라 `NBest[0].AccuracyScore`가 맞음) 오류 발생 → 고침.
     - 2차 시도: 구조는 맞았는데 이번엔 전부 0점/인식된 소리 없음으로 나옴. 원인으로 의심되는 것: Azure REST 문서는 오디오 포맷으로 `audio/wav`(PCM)와 `audio/ogg;codecs=opus`만 공식 지원한다고 명시하는데, 브라우저 MediaRecorder 기본 녹음 포맷인 `audio/webm;codecs=opus`는 이 목록에 없었음.
     - 3차 시도: MediaRecorder 대신 Web Audio API로 직접 PCM 샘플을 모아 16kHz mono WAV 파일을 만들어서 전송하도록 교체함 (공식 지원 포맷 그대로) → **인식 자체는 성공** (사용자가 콘솔 로그로 확인, RecognitionStatus: Success, DisplayText가 실제 발음대로 나옴).
     - 4차 수정(부분적): 최상위 `DisplayText`로 바꿔봤지만, 여전히 목표 글자 쪽으로 쏠려서 나옴("마차"→"아아", "건"→인식 안 됨). Pronunciation-Assessment 헤더에 참조 텍스트를 실어 보내면 **인식 결과 자체가 그 참조 텍스트 쪽으로 편향된다**는 게 원인으로 최종 확인됨 (Azure 공식 문서도 "정확한 인식 텍스트가 필요하면 먼저 일반 STT를 따로 호출하라"고 안내함).
     - 5차 수정: **같은 녹음 파일을 두 번 전송**하는 방식으로 바꿈 — ① `Pronunciation-Assessment` 헤더 없이 순수 인식(실제로 뭐라고 말했는지), ② 헤더를 넣어 발음 채점(점수만 사용). 화면에는 ①에서 얻은 진짜 인식 텍스트를 보여줌 → **인식 텍스트 표시는 정상 확인됨.**
     - 6차 수정(채점 로직 자체를 바꿈): 인식된 글자가 목표와 다른데도 Azure 점수가 100점으로 나오는 문제 발견 → **목표 글자를 정확히 맞혔을 때만 Azure 점수를 그대로 쓰고, 안 맞으면 우리가 직접 채점**하도록 바꿈. 한글을 초성/중성/종성으로 분해해서(`decomposeHangul`) 목표와 얼마나 겹치는지 유사도(0~1)를 계산(`jamoSimilarity`) → 2/3 이상 겹치면 "비슷하지만 틀림"(70점 미만, "발음이 틀렸어요" — 예: 막→망처럼 받침만 다름), 그보다 적으면 "아예 다른 소리"(20점 미만, "다시 발음해보세요").
     - 7차 수정: "나비"를 "가수"로 잘못 말해도 "비슷함"으로 분류되는 문제 발견 → 원인은 받침 없는 음절끼리는 "둘 다 받침 없음"이라는 이유만으로 유사도 점수를 자동으로 얻고 있었음(의미 없는 유사성). 받침이 둘 다 없을 때는 비교 대상에서 아예 빼도록 `jamoSimilarity` 가중치를 수정함.
     - 8차 수정(사용자 요청): 정확한 단어로 인식된 경우는 지금처럼 Azure 세부 점수를 계속 쓰되(무조건 100점으로 안 함 — 받침을 흐릿하게 발음하는 것도 잡아내는 게 원래 목적이라 유지하기로 함, 2026-08-31 확정), **100점이 아닐 때 왜 100점이 아닌지 이유를 같이 보여주도록** `explainLowScore` 함수 추가. Azure 응답의 `SNR`(소리 크기), `FluencyScore`(자연스러움), 음소별 `AccuracyScore` 중 가장 낮은 걸 보고 "소리가 작았어요" / "말이 끊겼어요" / "'ㄱ' 소리가 흐릿했어요" 식으로 이유를 표시.
   - **편의 기능 추가**: 듣기 화면에 "이전 문제" 버튼(첫 문항에서는 안 보임, 화살표 기호는 사용자 요청으로 뺌), 단계 목록 화면에 "📋 결과 확인" 버튼.
   - **결과 화면 구조 변경(사용자 요청)**: 단계에 들어갈 때마다 "시험 1회"로 묶어서(`state.sessions`) 기록. 결과 확인 화면은 세션별 평균 점수만 먼저 보여주고, 탭하면 문항별 점수 + **틀린 문항에만** 이유를 보여주는 상세 화면(`renderSessionDetail`)으로 이동.
   - **채점 기준 조정(사용자 요청 + 합의)**: 정확한 단어를 말했을 때 Azure 점수가 90점대여도 100점이 아니어서 혼란스럽다는 피드백 → 90점 이상은 사람 귀로 구별 안 되는 노이즈로 보고 **100점 처리**, 90점 미만(진짜 문제일 가능성이 높은 구간)만 실제 점수 + 이유를 보여주는 절충안 적용 (2026-08-31 확정).
   - `explainLowScore`에서 음소별 점수 추측 부분은 제거함 (필드명을 확신할 수 없고 실제로 이상한 문구가 나왔음) — 지금은 SNR(소리 크기)/FluencyScore(자연스러움)만 확인하고, 그 외엔 "받침이나 소리의 일부가 정확하지 않았어요"라는 일반적 문구를 보여줌.
   - 아직 사용자 재테스트 전.
   - **9차 수정(사용자 요청, 문항 다양화)**: 각 단계 문항이 항상 똑같은 3개였던 걸, 단계별로 10~18개짜리 단어 은행(`stages[i].items`)으로 늘리고, 단계에 들어갈 때마다 그중 무작위로 5개를 뽑아서(`shuffle` 함수) 그 세션에서 씀 (`state.sessionItems`). 07/08번 참고자료 원칙(의미단어+무의미단어 섞기, 대표받침 7개는 표기와 소리가 일치하는 것만) 반영해서 단어 목록 구성함.
   - **10차 수정(사용자 요청, 화면 통합)**: "듣기" 화면과 "말하기 연습" 화면이 따로 있어서 매번 "말하기 연습 →" 버튼을 눌러야 했던 게 번거롭다는 피드백 → **한 화면에 듣기 버튼 + 마이크 버튼 + 이전 문제 버튼을 모두 합침**(`renderListen`/`renderSpeak` → `renderPractice` 하나로 통합, 화면 이름도 `listen`/`speak` → `practice`로 통일).
   - **11차 수정(사용자 요청)**: "이전 문제" 버튼을 없애고 그 자리에 **"모르겠어요" 버튼**을 추가함 (`markDontKnow` 함수) — 학생이 모르는 문항을 눌러서 넘기면 그 문항이 세션 결과에 "모르겠다고 답함"으로 기록되어, 결과 확인 화면에서 선생님이 어떤 문항을 몰랐는지 확인할 수 있음. "단계 목록으로"는 왼쪽, "모르겠어요"는 오른쪽에 배치(`.nav-row` flex).
   - **12차 수정(사용자 요청, 디자인)**: 전체적으로 너무 둥글둥글해서 "바이브 코딩 느낌"이 난다는 피드백 → 카드/버튼의 `border-radius`를 대부분 4~8px로 줄이고, 마이크 버튼도 완전한 원(50%)에서 각진 사각형(8px)으로 바꿈.
   - **13차 수정(2026-09-02, 사용자 요청)**: 다른 컴퓨터로 이어서 첫 실전 테스트 중 "라"를 정확히 말했는데 "락"으로 잘못 인식되어 오답(67점) 처리되는 사례 발견. 사용자가 "Azure에 같은 녹음을 세 번 보내는 식으로 정확도를 높일 수 있냐"고 물어봄 → **같은 오디오를 여러 번 다시 보내는 건 Azure가 결정적으로 같은 답을 주기 때문에 효과가 없다고 판단**하고, 대신 이미 받는 응답 안의 정보를 더 활용하도록 바꿈: 순수 인식 응답의 1순위 후보만 보던 것을, Azure가 함께 주는 대체 후보 목록(NBest)까지 확인해서 그중 목표 글자와 정확히 일치하는 게 있으면 그걸 정답으로 인정하도록 `assessRecording` 로직을 수정함. 다만 이렇게 해도 한 음절만 따로 말하면 근본적으로 헷갈릴 수 있는 한계는 남아있어서, **오답 화면(다시 시도/다음 문제 버튼 아래)에 "잘 발음했어요 (선생님 확인)" 버튼을 추가**함 — 선생님이 옆에서 듣고 실제로는 맞았다고 판단하면 눌러서 그 문항을 정답(100점)으로 수동 정정하고 다음 문제로 넘어갈 수 있음.
   - 아직 사용자 재테스트 전 (특히 "잘 발음했어요" 버튼과 NBest 개선이 실제로 어떻게 동작하는지).
   - **14차 수정(2026-09-02, 사용자 요청, 점수 체계 세분화)**: 실전 테스트 중 "라"를 "락"으로 잘못 인식해 67점(비슷하지만 틀림)이 나온 걸 계기로, 사용자가 "자음 또는 모음 하나가 틀렸을 때 50점은 너무 높지 않냐"고 문제 제기함. 기존 로직은 초성/중성이 통째로 다른 경우(예: '가'→'나', 자음 단계의 핵심 오류)와 받침만 다른 경우(예: '막'→'망')를 구분하지 않고 하나의 유사도 숫자(jamoSimilarity)로 뭉뚱그려서, 완전히 다른 소리인데도 50점 안팎의 애매한 점수가 나오는 문제가 있었음. → **`compareSyllable`/`classifyMismatch` 함수를 새로 추가**해서 음절마다 '초성·중성 자체가 다름(diff)' vs '받침만 다름(jongDiff)'을 먼저 구분하도록 바꾸고, 점수 구간을 명확히 분리함: diff가 하나라도 있으면 0~29점("완전히 다른 소리"), 없고 jongDiff만 있으면 단어 내 정확한 음절 비율 기반으로 40~69점("받침만 다름", 받침 문제가 있으면 절대 70점 이상은 못 넘도록 상한 유지). 30~39점 구간은 두 등급이 숫자만 봐도 바로 구분되도록 일부러 비워둠. 함수 하나로 시뮬레이션해서 '가'→'나' 50→29점, '라'→'락' 67→40점, '고구마'→'고국마'(3음절 중 1음절만 받침오류) 67→69점으로 바뀌는 걸 확인함 (문법 검사 + node로 로직만 떼어내 시뮬레이션, 브라우저 실사용 재확인은 아직 못 함).
   - **주석 추가(2026-09-02, 사용자 요청)**: 코드를 공부하려는 목적으로 `index.html`, `api/get-token.js`, `dev-server.mjs`, `supabase/schema.sql` 전체에 함수/블록 단위 설명 주석을 달아둠 (로직 변경 없음, 백업과 diff로 확인함). 앞으로도 이 사용자의 코드는 학습 목적상 주석을 꼼꼼히 다는 것을 기본으로 함.

## 검토됨: 채점 등급(14차 수정)이 07/08번 참고자료의 지도 원리와 부합하는지

- 사용자 요청으로 [07번](07-발음지도-참고자료-요약.md)/[08번](08-찬찬한글-참고자료-요약.md) 문서를 다시 읽고 14차 수정(diff/jongDiff 등급 분리)을 대조 검토함.
- 결론: 부합함. "소리를 지도하는 순서: 초성 → 종성(받침), 받침 없는 글자 → 받침 있는 글자"(07번)와 "모음을 자음보다 먼저 가르친다 - 모음이 자음보다도 더 기초"(08번) 원리에 따라, 초성/중성 오류(diff)를 받침만 다른 오류(jongDiff)보다 더 엄격하게(0~29점 vs 40~69점) 채점하는 지금 방식이 "받침은 단계적으로 익혀가는 중인 스킬, 초성·중성은 이미 다져놨어야 할 기초"라는 위계와 맞음.
- **나중에 반드시 다시 봐야 할 것**: 07번 문서는 "음운변동(연음·비음화·구개음화·ㅎ탈락)"을 **받침가족 단계 이후**에 반영할 예정이라고 명시함. 지금 6단계(대표받침) 단어는 표기와 소리가 일치하는 것만 골라둬서 문제 없지만, 나중에 받침가족·겹받침 단계를 추가해서 음운변동이 있는 단어(예: "국물"이 실제로는 "궁물"로 소리 나는 게 정답)를 다루게 되면, 지금의 jongDiff 채점 로직이 **이 정상적인 발음 변화까지 오답으로 잘못 채점**하게 된다. 그 단계를 만들 때 채점 로직을 반드시 함께 손볼 것.
- (참고, 지금 당장 할 필요는 없음) 08번 문서는 모음이 자음보다도 더 기초라고 설명하는데, 지금은 초성 오류와 중성 오류를 diff 하나로 묶어서 똑같이 채점한다. 필요하다고 판단되면 모음 오류를 자음 오류보다 한 단계 더 낮은 점수로 나누는 세분화도 가능하나, 지금 세분화만으로도 충분해 보여 보류함.

## 학생 관리 기능 (구현 완료, Supabase 서버 연결까지 됨)

사용자가 "한글또박또박" 같은 기존 검사 프로그램(스크린샷)을 참고 사례로 보여주며 요청. 원래는 "1~6단계 먼저 마무리 후 착수"로 정했었는데, 사용자가 자리를 비우며 "지금 바로 만들어달라"고 요청해서 2026-08-31에 구현함.

- **로그인**: 이름 + 비밀번호. 처음 쓰는 이름이면 그 자리에서 새 계정으로 만들어짐(가입 절차 따로 없음). `handleLogin`.
- **반 관리**: 로그인 후 반 목록 화면(`renderClassList`), "+ 반 추가"로 반 생성.
- **학생 목록**: 반을 고르면 학생 목록 화면(`renderStudentList`) — 번호/이름/평균 점수 표, "검사 시작"(그 학생으로 1~6단계 연습 진입), "결과 보기"(그 학생의 세션 기록), 삭제.
- **학생 수 추가**: 원하는 인원수만큼 빈 학생 행을 한 번에 추가(번호 자동 증가, 이름은 표에서 바로 입력).
- **엑셀 업로드/양식**: SheetJS(xlsx, CDN)로 구현. 양식은 **1열=번호, 2열=이름**, 첫 줄은 헤더로 취급해 건너뜀. "엑셀 양식 다운로드" 버튼으로 견본 파일을 내려받을 수 있음(`downloadStudentTemplate`). 업로드는 `handleExcelUpload`에서 파싱.
- **버그 수정**: "반 추가" 버튼이 반응 없다는 피드백 → 원인은 `window.prompt()` 팝업이 이 환경에서 조용히 안 뜨는 것으로 추정됨. `prompt()`/`confirm()`/`alert()` 같은 브라우저 네이티브 팝업을 전부 화면 안 입력창/문구로 바꿈 (반 추가는 입력창+버튼, 학생 삭제는 "한 번 더 누르면 삭제" 2단계 클릭, 로그인/엑셀 오류는 화면에 빨간 문구로 표시).

### Supabase 서버 연결 (완료, 2026-08-31)

- **DB**: Supabase 선택함 (Vercel Postgres보다, 로그인 기능이 내장돼 있고 대시보드에서 데이터를 직접 볼 수 있어서). 사용자가 Supabase 프로젝트 생성 후 Project URL / publishable key / secret key 전달함.
  - Project URL, publishable/secret key는 `.env.local`에 저장 (git 제외).
  - publishable key는 브라우저에 그대로 노출해도 안전하도록 설계된 키라서 `index.html`에 상수로 직접 넣음. secret key는 지금은 어디에도 안 쓰고 있음(나중에 서버 전용 관리 기능이 필요해지면 사용).
- **DB 구조**: [supabase/schema.sql](../supabase/schema.sql) 파일로 정의함 — `classes`(반), `students`(학생), `sessions`(학생별 단계 검사 기록, `items`는 jsonb) 3개 표. Row Level Security로 "선생님은 본인이 만든 데이터만" 접근 가능하게 제한함. **사용자가 Supabase 대시보드 SQL Editor에서 직접 실행해야 적용됨** — 실행 여부 다음 세션에서 확인 필요.
- **로그인 방식**: Supabase Auth(이메일+비밀번호) 사용. 다만 실제 이메일 없이 "이름+비밀번호"만으로 쓰게 하려고, 이름을 결정적 해시로 변환해 가짜 이메일(`t{해시}@hangeul.local`)을 만들어 내부적으로만 씀 (`emailFor` 함수). 처음 쓰는 이름이면 그 자리에서 자동 가입(`signUp`), 있으면 로그인(`signInWithPassword`).
  - **사용자가 Supabase 대시보드에서 "Confirm email"을 꺼야만** 가입 즉시 로그인이 됨(안 끄면 이메일 인증 대기 상태가 되어 로그인 실패) — 다음 세션에서 이것도 확인 필요.
- **CDN 로드**: `supabase-js@2`를 `https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2`로 불러옴 (설치 없이 사용).
- 로그인 후 `loadClasses()`로 반+학생+검사기록을 한 번에 불러와 `state.classes`에 캐시하고, 이후 추가/수정/삭제할 때마다 Supabase에 즉시 반영(`insert`/`update`/`delete`) + 로컬 캐시도 같이 갱신. 검사 점수는 `saveSessionItems()`로 매 문항마다 저장.

### 구글 로그인 연동 (2026-09-02, 코드는 완료·Google/Supabase 대시보드 설정은 사용자 확인 필요)

- 기존 이름+비밀번호 로그인은 그대로 두고, 로그인 화면에 "🔵 구글 계정으로 로그인" 버튼을 추가하는 방식(대체가 아니라 추가)으로 구현함.

  3. Supabase 대시보드 > Authentication > Providers > Google 활성화 → 위 Client ID/Secret 입력 → 저장 (이 키들은 Supabase 쪽에만 등록하면 되고, 우리 프로젝트의 `.env.local`이나 Vercel 환경 변수에는 넣지 않는다 - Supabase가 구글과의 통신을 대신 처리해주기 때문).
  4. Supabase 대시보드 > Authentication > URL Configuration > Redirect URLs에 `http://localhost:3000` 추가 (로컬 테스트용, 나중에 Vercel 배포 주소도 추가해야 함).
- 사용자가 Google Cloud Console에서 OAuth 클라이언트 생성 완료, Supabase Provider에 Client ID/Secret 등록 완료. Redirect URLs에 `http://localhost:3000` 추가까지 안내함. **브라우저로 실제 "구글로 로그인" 버튼 클릭 테스트는 아직 결과를 못 받음** - 다음 세션에서 제일 먼저 확인.

### 결과 화면 재설계 + 검사지 리포트 + 학생 특성 체크박스 (2026-09-02)

- 사용자가 결과 확인 화면이 "시도한 순서대로"라 헷갈리고 전문적이지 않다고 피드백 → `renderHistory`를 **커리큘럼 단계(1.모음~6.대표받침) 순서로 묶어서** 보여주도록 재설계함. 각 단계는 카드 형태로 "최근 점수 + 도달/보완 필요 배지 + 시도 횟수"를 보여주고, 한 단계를 여러 번 시도했으면 탭했을 때 시도 목록(`renderStageAttempts`, 신규 화면)을 먼저 보여준 뒤 문항별 상세(`renderSessionDetail`)로 들어가게 함 (한 번만 시도했으면 목록 없이 바로 상세로).
- 참고용으로 보여준 "한글또박또박" 검사지 스크린샷을 본떠서 **인쇄 가능한 검사지 리포트**(`renderReport`, 신규 화면)를 추가함. 학생 목록의 "리포트" 버튼으로 진입. 학생 정보(반/번호/이름/다문화/기초학습지원대상) 표 → 종합결과(검사일시/전체 평균/수준) 표 → 자동 생성 종합의견(보충 필요 항목 나열, 없으면 칭찬 문구) → 항목별 세부결과 표(단계명/맞은 문항 수 대비 전체/도달여부/오반응 목록) 순서로 구성. 별도 PDF 라이브러리 없이 `@media print` CSS + `window.print()`만으로 인쇄/PDF 저장을 지원함 (결과물 형식 우선순위 원칙에 맞게 외부 라이브러리 추가를 피함).
- 학생별 **"다문화"/"기초학습지원대상" 체크박스**를 학생 목록 표에 추가함(사용자 요청). Supabase `students` 테이블에 `multicultural`, `basic_support` 불리언 컬럼 추가 필요 — **`supabase/schema.sql` 맨 아래 "마이그레이션" 섹션의 `alter table` 두 줄을 SQL Editor에서 한 번 더 실행해야 실제로 작동한다** (기존 `create table if not exists`는 이미 있는 테이블에는 적용 안 됨). 체크박스를 누르면 바로 Supabase에 저장됨.
  - 참고: 이 두 항목은 "이름+점수" 수준을 넘어서는 학생 개인정보라서, [00번 가이드](00-프로젝트-에이전트-가이드.md)의 "저장 항목 최소화" 원칙에서 벗어나는 확장이다. 다만 접근 제어(RLS)는 테이블 전체에 이미 적용돼 있어 별도 보안 설계 없이도 "선생님 본인 반만" 원칙은 그대로 유지됨. 사용자가 프로토타입 단계에서 개인정보 정식 검토는 생략하기로 명시적으로 결정함(2026-09-02).
- 문법 검사 + node로 리포트 집계 로직(단계별 최근 시도 찾기, 전체 평균, 실패 단계 목록)만 따로 시뮬레이션해서 확인함. **브라우저로 실제 화면 확인은 아직 못 함** - 다음 세션에서 확인 필요.

### 사용자 실사용 피드백 반영 (2026-09-02, 위 기능들 실제로 써본 뒤)

1. **다문화/기초학습지원대상 저장 안 됨** — "Could not find the 'basic_support' column" 오류 발생. 원인은 위 마이그레이션 SQL을 아직 Supabase에서 실행하지 않아서. 코드 문제 아님 — 다음 세션 시작할 때 실행 여부부터 확인.
2. **세션 상세 화면에 "무엇으로 오발음했는지" 안 보임** — 그동안 `session.items`에 인식된 소리(recognizedText)를 아예 저장하지 않고 있었음(맞았는지/점수/이유만 저장). `assessRecording`에서 `recognizedText`도 함께 저장하도록 고치고, `renderSessionDetail` 표에 "인식된 소리" 열을 추가함.
3. **세션 상세 표에 헤더(열 이름)가 없었음** — "문항/점수/인식된 소리/오류 내용" 헤더 행을 추가함.
4. **결과 화면들에서 학생 목록으로 바로 못 감** — `renderHistory`와 `renderSessionDetail`에 기존 버튼("단계 목록으로"/"결과 목록으로")은 그대로 두고 **"학생 목록으로" 버튼을 나란히 추가**함 (어디서 들어왔든 한 번에 학생 목록으로 돌아갈 수 있게).
5. **검사지 리포트에 "4. 추천 학생 지도 방안" 추가** — 실시간 AI 호출(Claude API) vs 규칙 기반 미리 작성한 문구 중 사용자가 **규칙 기반**을 선택함(유료 API/서버 불필요, 인터넷 없이도 동작, 오늘 안에 완성 가능해서). `STAGE_ADVICE`에 07/08번 문서 내용을 바탕으로 단계별 지도 문구를 미리 써두고, `buildAdviceList`가 "보완 필요"로 나온 단계의 문구만 골라 보여줌. 실시간 AI 호출 옵션은 안 씀 — 나중에 필요하면 재검토.

### 위 5가지를 실제로 써본 뒤 다시 받은 피드백 (2026-09-02, 같은 날 두 번째 라운드)

- **2번 관련**: "인식된 소리"가 계속 "-"로만 나온다는 피드백 → 확인해보니 실제로는 정상 동작이었고, 사용자가 보고 있던 세션이 `recognizedText`를 저장하기 **이전**(이날 세션 초반)에 만들어진 오래된 기록이라 그 필드 자체가 없었던 것뿐이었음(코드 버그 아님). 다만 화면에 "-"만 뜨면 마치 고장난 것처럼 보이므로, `renderSessionDetail`에서 "예전 기록이라 없음"과 "인식은 했지만 소리를 못 얻음"을 구분해서 보여주도록 문구를 다듬음. **새로 시작하는 검사부터는 정상적으로 인식된 소리가 보여야 함** — 다음 세션에서 새 세션으로 재확인 필요.
- **리포트의 "오반응" 표시 방식 개선**: 기존엔 오답 글자만 나열했는데(예: "버스, 수바"), "문항이 뭐였고 어떻게 오반응했는지"가 더 중요하다는 피드백 → `formatWrongItem` 함수를 추가해서 "문항→인식된 소리"(예: "버스→거스") 형태로 표시하도록 "3. 항목별 세부 결과" 표를 바꿈. "모르겠어요"로 넘긴 문항은 "문항(모르겠음)"으로 구분 표시.
- **"4. 추천 학생 지도 방안" 문구 개선**: "특히 '워'에서 오류가 보였어요"처럼 단어 하나만 콕 집는 문구는 필요 없고, **무엇이 부족한지(받침 발음, 받침 탈락 등)를 유형별로 상세히 설명**해달라는 요청 → `summarizeErrorTypes` 함수를 추가해서, 그 단계의 오답들을 채점 피드백 문구 기준으로 "받침 탈락/교체" / "초성·중성 자체가 다른 더 기초적인 오류" / "발음은 맞았지만 소리 크기·유창성 감점" / "아예 모르겠다고 답함" 네 유형으로 나눠서, 각 유형이 있을 때만 그 유형 설명 + 해당 문항 목록을 문장으로 붙여 보여주도록 바꿈.
- 위 항목들 모두 문법 검사 + node 시뮬레이션으로 로직만 확인함. 브라우저 실사용 재확인 필요.

### 세 번째 라운드 피드백 (2026-09-02, 실제 검사 중 "따" 발음 사례)

- **"따"를 정확히 발음했는데 58점(불합격)이 나와서 이상하다는 피드백** → 확인해보니 버그가 아니라 정상 동작: "인식된 소리: 따"로 목표와 정확히 일치했지만, Azure의 세부 점수 중 유창성(FluencyScore)이 낮게 나와서(`explainLowScore`가 "말이 자연스럽게 이어지지 않았어요" 이유를 보여줌) 그대로 낮은 점수를 준 것. 정확한 단어를 말해도 발음 품질이 떨어지면 낮은 점수를 주는 게 Azure 발음 평가를 쓴 원래 목적([10번 문서](10-음성인식-기술-선택.md))이라 의도된 동작이지만, 짧은 한 음절만 녹음하면 "유창성" 지표 자체가 원래 여러 음절/문장에 최적화된 지표라 불안정할 수 있다는 가능성은 남아있음 - 나중에 이런 사례가 자주 보이면 단음절 단계(1~2단계)에 한해 FluencyScore 비중을 낮추는 걸 검토하기로 함 (아직 코드는 안 건드림).
- 리포트의 "오답 문항"/"인식된 소리"가 같은 글자로 나란히 보이는 게(예: "따" | "따") 이 상황을 오히려 명확하게 보여준다는 걸 확인함(아래 표 개편 덕분).
- **리포트 표 가독성 개선**: "오반응" 한 칸에 "빠→봐, 까→가, 따→따"처럼 여러 개를 몰아넣던 걸, **"오답 문항"과 "인식된 소리" 두 열로 분리**(줄바꿈으로 문항별로 나란히 대응)해서 한눈에 보기 쉽게 바꿈.
- **"4. 추천 학생 지도 방안" 구조 개편**: 한 문단에 다 이어붙이던 걸 **"1. 2. 자음" 같은 큰 항목 + "가/나/다..." 하위 항목**(기본 지도 원리 한 줄 + 오류 유형별 설명 한 줄씩) 구조로 바꿈 (`renderAdviceSection` 신규, 기존 `buildAdviceList`/`formatWrongItem` 대체). 하위 항목의 예시 글자도 화살표 없이 문항 이름만 나열하도록 단순화함(어떤 소리로 들렸는지는 이제 표에서 바로 보이므로 중복 설명 제거).
- 문법 검사 + node 시뮬레이션으로 확인함. 브라우저 실사용 재확인 필요.

### 오류 유형 진단 태그 추가 (2026-09-02, 네 번째 라운드)

- 사용자가 세션 상세 화면의 "오류 내용"도 07/08번 문서 용어(받침 탈락 등)로 더 전문적으로 표기해달라고 요청.
- **`analyzeError(it)` 함수 신설** — 오답 문항 하나의 목표 글자와 인식된 소리를 초/중/종성 단위로 직접 비교해서, "받침 탈락"/"받침 첨가"/"받침 교체"/"초성(자음) 오류"/"중성(모음) 오류"/"음절 수 오류"/"유창성·음량 문제"/"모름"/"인식 실패" 중 해당하는 태그를 (한 문항에 여러 개 겹칠 수 있어서) 배열로 반환함. `classifyMismatch` 바로 아래에 정의해서 세션 상세 화면과 리포트 지도 방안이 똑같은 기준을 공유하도록 함(기존엔 각자 다른 방식으로 오류를 나누고 있었음).
  - 예: '까'→'가'는 ["초성(자음) 오류"], '막'→'마'는 ["받침 탈락"], '강'→'감'은 ["받침 교체"], '라'→'락'은 ["받침 첨가"], 정확히 인식됐지만 저품질인 경우(예: '따'→'따')는 ["유창성/음량 문제"].
- `renderSessionDetail`의 "오류 내용" 칸에 이 태그를 작은 주황색 배지(`.error-tag`)로 보여주고, 그 아래 기존 안내 문구(it.feedback)를 작게 함께 보여주도록 바꿈.
- 리포트의 `summarizeErrorTypes`도 자체적인 feedback 문자열 매칭 대신 `analyzeError`+`ERROR_TAG_DESC`를 재사용하도록 리팩터링함 (한 곳만 고치면 두 화면 모두 반영됨).
- node로 '빠'→'봐'(초성+중성 오류), '까'→'가'(초성 오류), '따'→'따'(유창성 문제), '막'→'마'(받침 탈락), '강'→'감'(받침 교체), '라'→'락'(받침 첨가) 등 사례를 시뮬레이션해서 전부 의도대로 분류되는 걸 확인함. 브라우저 실사용 재확인 필요.

### 다섯 번째 라운드 피드백 - 가독성 + 문구 통일 + 지도법 추가 (2026-09-02)

1. **세션 상세 화면 가독성 개선**: 오류 태그 아래에 "목표 글자와 다른 소리예요. 다시 발음해보세요" 같은, 태그만으로 이미 다 설명되는 뻔한 문구가 매번 반복돼서 지저분하다는 피드백 → `GENERIC_FEEDBACK_TEXTS` 집합을 만들어 이 문구들(받침이 정확하지 않아요/목표 글자와 다른 소리예요.../모르겠다고 답함)은 태그 아래에 다시 보여주지 않고, 태그만으로 설명 안 되는 진짜 세부 사유(SNR·유창성 등 explainLowScore 문구)일 때만 보여주도록 바꿈. 또한 이 화면이 좁은 카드(480px)에 4열짜리 표를 욱여넣어 글자가 한 자씩 줄바꿈되던 문제 → `sessionDetail`을 `WIDE_SCREENS`에 추가하고 표 스타일도 기존 `.data-table`과 같은 계열인 `.report-table`로 통일함.
2. **리포트 표 가독성 개선(2차)**: "오답 문항"/"인식된 소리"를 한 칸에 `<br>`로 여러 줄 쌓아서 줄 수로 대응시키던 방식이 여전히 헷갈린다는 피드백 → 오답 문항 하나당 표의 행(`<tr>`)을 아예 하나씩 따로 만들고, "항목/점수/도달여부" 3칸은 `rowspan`으로 묶어 한 번만 보여주는 구조로 바꿈(실제 진단 보고서에서 흔히 쓰는 표 구조). 단계가 바뀌는 첫 행 위에는 옅은 굵은 선을 그어 단계끼리 시각적으로 구분함.
3. **지도 방안 문구 통일 + 유형별 지도법 추가**: "받침보다 더 기초적인 오류 (빠, 까)."처럼 묘사만 하고 끝나는 문장과, "~연습시켜보세요"로 끝나는 실행 지침이 섞여 있어 통일감이 없다는 피드백 + 오류 유형마다 구체적으로 어떻게 지도하면 좋을지 추천해달라는 요청 → `ERROR_TAG_DESC`(설명만 있던 사전)를 **`ERROR_TAG_ADVICE`(문항 목록을 받아 "무엇이 문제였는지 + 어떻게 지도하면 좋을지"를 한 문장으로 만드는 함수 사전)로 교체**하고, `STAGE_ADVICE`의 6개 문장도 전부 "~연습시켜보세요"로 끝나게 다듬음. 유형별 지도법:
   - **받침 탈락**(예: 막→마): 받침 소리를 과장해서 들려주고 끝까지 붙여 말하는 연습
   - **받침 첨가**(예: 라→락): 받침 없는 글자와 있는 글자를 나란히 비교하는 연습
   - **받침 교체**(예: 강→감): 같은 자리에서 받침만 다른 낱말끼리(강/감/간) 비교하는 연습
   - **초성(자음) 오류**: 조음 위치가 비슷한 자음끼리(ㅁ↔ㅂ, ㅇ↔ㄱ) 입 모양을 비교하는 연습
   - **중성(모음) 오류**: 천지인 원리로 입 모양·밝은소리/어두운소리 차이를 비교하는 연습
   - **음절 수 오류**: 글자를 하나씩 손으로 짚어가며 음절 수만큼 끊어 읽는 연습
   - **유창성/음량 문제**(예: 정확히 인식된 '따'가 저품질): 목소리를 크고 끊기지 않게 이어 말하는 연습
   - **모름/인식 실패**: 다시 들려주고 따라 말하기부터, 또는 마이크에 더 가까이 말하도록 안내
- 문법 검사 + node 시뮬레이션(표 rowspan 구조, 문구 생성)으로 확인함. 브라우저 실사용 재확인 필요.

### git push 전 코드 리뷰 (2026-09-03)

push 전 diff를 다시 훑어보며 2가지를 고침:

1. **주석 위치가 엉킴**: 로고 클릭 이벤트를 추가하면서 그 설명 주석이 `getSession()` 관련 기존 주석과 그 주석이 설명하는 실제 코드(IIFE) 사이에 끼어들어감 → 로고 클릭 코드+주석을 그 앞으로 옮겨서 원래 주석이 자기가 설명하는 코드 바로 위에 오도록 정리.

## git push 전 코드 리뷰 (2026-09-02, 첫 배포 전)

[00번 가이드](00-프로젝트-에이전트-가이드.md)에 새로 정한 "git push 전 습관"에 따라, 오늘 쌓인 변경사항을 push하기 전에 `/code-review` 스킬로 자체 검토를 거침. 발견된 4가지를 모두 그 자리에서 고침:

1. **세션 상세 화면 오표시**: "모르겠어요"/"잘 발음했어요(선생님 확인)"으로 만들어진 항목(둘 다 recognizedText 필드가 아예 없음)이 "(예전 기록)"으로 잘못 표시되던 문제 → feedback 문구로 먼저 구분해서 "(모르겠음)"/"(선생님 확인)"으로 정확히 표시하도록 고침.
2. **Chart.js 로드 실패 대비 없음**: 엑셀 라이브러리(XLSX)는 `typeof XLSX === 'undefined'` 체크가 있는데 Chart.js는 없어서, CDN이 막힌 환경(오프라인 교실 등)에서 학급통계를 열면 흰 화면으로 깨지던 문제 → `chartAvailable` 체크를 추가해서, 그래프 라이브러리를 못 불러왔으면 각 차트 자리에 안내 문구를 대신 보여주도록 고침.
3. **자동 로그인 확인에 try/catch 없음**: 페이지가 열릴 때 `sb.auth.getSession()`이 실패하면(저장된 로그인 정보 손상 등) 어느 화면도 안 그려지고 완전히 빈 화면으로 멈추던 문제 → try/catch로 감싸서, 실패해도 로그인 화면으로 안전하게 넘어가도록 고침.
4. **학생/반/선생님 이름 미이스케이프**: 이름에 `<`, `>`, `&`, `"` 같은 문자가 들어있으면 화면이 깨지거나(리포트 표 등) 학생 이름 입력칸이 통째로 깨질 수 있던 문제(입력칸은 `value="..."` 속성 안에 그대로 넣고 있어서 특히 위험했음) → `escapeHtml()` 함수를 새로 만들어 학생 이름·반 이름·선생님 이름이 화면에 나가는 모든 지점에 적용함. (참고: Azure 인식 결과는 `normalizeHangul`이 한글 완성형 문자만 남기므로 애초에 위험한 문자가 나올 수 없어 이스케이프가 필요 없음 - 코드 리뷰에서도 이 지점은 제외하고 판단함.)

node 시뮬레이션으로 4가지 모두 고쳐졌는지 재확인함(Chart 미정의 상태에서 fallback 문구가 뜨는지, 이름에 `<script>` 태그를 넣어도 그대로 이스케이프되는지 등). 이 정리를 마친 뒤 커밋 + `git push` 진행.
